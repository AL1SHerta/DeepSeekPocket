2数据口径：为什么「今日用量」只能这么算

2.1 官方接口能力的核查结论

DeepSeek 官方 API（api-docs.deepseek.com）目前公开的端点共 10 个，全部是对话/补全、文件、模型列表与余额查询，其中：

  • 没有历史用量接口、没有账单接口、没有按模型或按 Key 的用量聚合接口；
  • GET /user/balance 只返回当前时刻的账号级余额快照（总额、赠金、充值），不带时间维度；
  • 余额是账号级的，同一个账号下所有 API Key 共享同一份余额 —— 因此「每个 Key 分别用了多少」在物理上就无法从官方数据得到。
因此本应用不做的事：不伪造用量数字，不把「余额差」直接等同于「消费额」，不宣称提供了官方账单， 也不调用任何社区私有接口或猜测出来的端点。

2.2 实际采用的算法

每次余额查询成功，落一条采样（币种、总额、赠金、充值额、时间戳）。「今日用量」由当天采样序列推出：

// 今日 = 北京时间 00:00 起，按时间升序
usage = 0
for i in 1 until samples.size:
    delta = samples[i-1].total - samples[i].total
    if delta > 0:   usage += delta        // 余额下降 → 计入用量
    if delta < 0:   hasRecharge = true    // 余额上升 → 视为充值，跳过

把「上升」单独标记而不是相互抵消，是为了避免一笔充值把当天真实消耗抹掉。UI 上会额外提示「期间检测到充值，余额上升的部分未计入用量」。

采样方式
离散采样：只在应用查询余额时记录
最小可用条件
当天 ≥ 2 条采样才能算出变化
已知误差来源（已在 UI 内明示）： ① 采样间隔内的多笔消耗会被合并成一次下降，无法拆分到时刻； ② 应用没在运行时不会采样，因此「覆盖起点」之前的消耗无法回溯； ③ 金额一律以十进制字符串存储并参与计算，不用浮点数，避免累加误差。

3.3 判定实现要点

  • 在 UTC 时区下判断星期与时刻，严格照抄官方口径，而不是在北京时间上做偏移猜测；
  • 窗口边界左闭右开：[01:00, 04:00)，所以 04:00 整点已经算错峰；
  • 倒计时不是「下一个窗口边界」，而是「下一次状态真正翻转的时刻」—— 例如周五 10:00 UTC 之后虽然跨过了一个窗口边界，但前后都算错峰，真正翻转要等到下周一 01:00 UTC；
  • 状态每 30 秒重算一次，跨过时段边界时界面会自己更新，不需要手动刷新。
明确的能力边界：官方规则还排除「中国法定节假日」，但节假日安排逐年由国务院公布且会调休， 本应用不内置也无法离线可靠推断。因此节假日当天会被当作普通工作日计算，可能被误判为高峰。 UI 上已如实写出这一条，不假装准确。

为什么刷新要分「前台」和「后台」两套

这不是偷懒，是 Android 的硬性规则：应用在后台无法按秒级定时轮询， WorkManager 的周期任务最小间隔就是 15 分钟。所以设置页里 秒级的刷新间隔只在前台生效，后台交给 WorkManager， 两者在界面上分别写明，不含糊其辞。

10峰谷判定为什么要内置一张节假日表

官方定价页写得很清楚：高峰是 UTC 01:00–04:00 与 06:00–10:00，周一至周五， 且排除中国法定节假日；其余时间（含整个周末、整个法定节假日）都是错峰。 也就是说，「今天是不是工作日」不只看星期几，还要看它是不是中国的法定节假日或调休上班日。

为什么不去读系统日历

你问过能不能读日历，我当时否掉了，理由有四条：

  • READ_CALENDAR 授予的是读取设备上全部日程的权限，为了判断节假日索要这个权限属于过度授权，违反最小权限原则。
  • 部分 ROM 根本没有节假日订阅日历，数据不一定存在。
  • 日历事件标题是自由文本（「国庆节」「十一假期」「放假」），无法可靠解析成日期区间。
  • 应用商店把日历列为敏感权限，需要证明核心用途；简历项目上架或面试被问到都会是减分项。

于是改成内置一张静态表，零新增权限：数据来自国务院办公厅 2025-11-04 发布的《关于 2026 年部分节假日安排的通知》，并抓取中国政府网与人民网两个来源交叉核对，文字一致。

为什么「调休上班日」也必须记

这是最容易被漏掉、一漏就错的地方：2026-10-10 是周六，但因为国庆调休要上班。 如果只按星期几判断，这天会被当成周末而算成错峰——而它其实要按高峰价计费。 所以表里同时存两份数据：33 个放假日 + 6 个调休上班日。 

// HolidayCalendar.kt — 三态判定，顺序不能换
fun isWorkingDay(date: LocalDate): Boolean = when {
    date in holidays        -> false   // 法定节假日 → 全天错峰
    date in makeupWorkdays  -> true    // 调休补班 → 当工作日算
    else                    -> date.dayOfWeek.value <= 5
}

11电池优化与日志安全

你提的两件事——「系统可能在后台冻结应用」和「日志会不会打印完整 Key」——分别是这样处理的。

电池优化：只读状态 + 带你去系统设置

设置页新增「电池优化」卡片，实时读取 PowerManager.isIgnoringBatteryOptimizations()： 未加入白名单时显示「仍受电池优化限制」并给出「去设置」，已加入时显示「已豁免电池优化」。 每次回到该页都会重新读一次，用户在系统设置里改完切回来能立刻看到变化。

刻意不申请权限：想直接弹系统确认框需要声明 REQUEST_IGNORE_BATTERY_OPTIMIZATIONS， 而该权限只允许闹钟、VoIP 等少数类别的应用使用，普通应用声明后上架会被拒。 所以这里只做两件事：读取状态（无需权限）、打开系统电池优化列表（无需权限）， 是否加白名单由用户自己决定。

  • 源码中 零个 Log.d/i/w/e 调用，也没有 OkHttp 的 HttpLoggingInterceptor，即不存在把 Authorization 头写进 logcat 的代码路径。

  • 新增 7 个泄漏回归测试（ApiKeyLeakTest）：对 401 / 429 / 500 / 响应体畸形 / 网络中断 / 成功响应 / 空 Key 七种情形，断言 userMessage、异常 message、toString() 都不含 Key、不含「Bearer」、不含 Key 的尾段片段。任何一次重构只要把 Key 拼进异常就会立刻变红。
